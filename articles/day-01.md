# 咖啡 Bot 做完之後，我想帶著原本的專案認識 Google ADK

Google ADK，全名是 Agent Development Kit，是 Google 提供的開源 AI agent 開發框架。它讓開發者把模型、工具和執行流程組織在一起，用來建立能完成任務的 agent 應用。[官方介紹](https://adk.dev/)

如果先用我自己的話理解：Gemini 負責理解與生成內容，ADK 則協助安排這些能力怎麼被使用、步驟怎麼接起來。

這樣說還是有點抽象，所以今天，我想帶著之前做好的 LINE Cafe Bot，開始認識這個對我來說全新的工具。

前一個系列，我和 Codex 一路替咖啡 Bot 加上找店、收藏、偏好記憶、安排時間、群組投票和咖啡護照。從「今天想去哪裡喝咖啡」，到約好時間、真的出發，再記下喝完之後的感受，已經累積了一段完整的旅程。

功能系列告一段落後，這個專案也剛好可以成為下一段學習的教材。

我也是第一次接觸 ADK，最想先弄懂的是：

> 我的咖啡 Bot 已經會呼叫 Gemini，也能讀資料、做推薦。那 ADK 會放在哪裡，又能幫我做什麼？

接下來，我打算用十五天，每天理解一點、實作一點，再把學到的內容寫下來。第一天先從自己熟悉的咖啡護照出發。

## 一句「本月咖啡護照」，背後其實有好幾步

原本在 LINE 輸入「本月咖啡護照」，最後會看到造訪次數、不同店家、平均評分，以及一小段 Gemini 寫的回顧。

但卡片出現以前，程式得先完成幾件事：確認發話者、讀取足跡與收藏、計算統計、產生摘要，最後再組成 LINE 訊息。

今天我先把這條流程畫出來，並在每個節點旁標上由誰處理：

- LINE 收到指令：程式負責接收事件與確認使用者。
- 資料讀取：程式取得這個人的足跡與收藏。
- 統計：程式計算次數、店家數與平均分數。
- 摘要：Gemini 根據統計，寫成兩句自然的回顧。
- LINE 回覆：程式把結果組成訊息並送出。

拆開之後就比較清楚了：整個流程裡，只有摘要這一步需要生成文字。讀取資料、算平均分數和組成訊息，都有明確的程式規則。

接下來想用 ADK 練習的，就是把這些步驟組織起來，讓先後順序、資料交接和不同情況的處理方式更容易看懂。

## 第一個概念：把流程想成一張 graph

Graph 可以先想成一張由節點和連線組成的圖。一個節點做一件事，連線描述工作之間的關係。

咖啡護照可以先縮成這三步：

**讀取紀錄 → 計算統計 → 產生回顧。**

統計需要先拿到紀錄，回顧又需要先知道統計結果，因此順序有明確的理由。

如果這個月沒有任何紀錄，流程也可以分成另一條路：直接提醒使用者先記下第一次造訪。有資料才產生回顧，零筆就顯示空狀態。

ADK 的 graph workflow 能把這些步驟與關係定義在程式裡。節點可以是一般函式、工具或 AI agent，因此一張圖裡可以同時安排程式與模型的工作。[官方 graph workflow 說明](https://adk.dev/graphs/)

## 今天先跑了一個沒有 AI 的小流程

為了先看懂資料怎麼移動，我今天執行了 repo 裡的離線範例：`node examples/day01-flow.mjs`。

這個範例使用虛構的咖啡足跡，由三個一般 JavaScript 函式依序完成讀取、統計與顯示文字。

示範資料共有三筆造訪，其中兩筆屬於同一家店，評分分別是 5、4、3。整理後的結果是：

> 3 次造訪、2 家不同的店，平均 4 分。

這裡很容易看懂「次數」與「店家數」為什麼要分開。同一家店去了兩次，造訪次數會增加，店家數仍然只算一家。

接著，我再執行 `node examples/day01-flow.mjs --empty`，切換成沒有紀錄的情境。

這次造訪次數和店家數都變成 0，平均分數是 null，最後顯示：

> 目前沒有示範紀錄，可以先記下第一次咖啡體驗。

null 在這裡表示沒有可計算的平均分數。沒有評分，和平均得到 0 分，是不同的意思。

兩種情境都跑過後，我比較能把輸入、處理步驟與輸出連在一起看：同一條流程收到不同資料，就會得到不同結果。

這個練習還沒有執行 ADK，也沒有呼叫 Gemini。最後的摘要是固定文案，先用來觀察資料流；之後才會把需要生成文字的節點接上模型。

## 把 Firestore 和 Cloud Tasks 放到圖外，角色就更清楚了

畫完主流程後，我也在旁邊補上原本專案已經用過的 Firestore 與 Cloud Tasks，替它們各寫下一句責任。

**Firestore：保存使用者的咖啡足跡、收藏與行程，讓程式之後可以查詢。**

它提供主流程需要的資料。對話重新開始，過去留下的足跡仍然應該保存在資料庫裡。

**Cloud Tasks：保存排程任務，在指定時間觸發提醒處理程式。**

例如原本的咖啡提醒，需要到時間再傳 LINE 訊息，就會用到這類排程能力。查看咖啡護照則先走資料讀取、統計與摘要的主流程。

這樣放回整張圖，我就比較不會把「安排工作順序」、「永久保存資料」和「到時間觸發工作」混在一起。

## 今天最想記住的，是 ADK 與 Gemini 的分工

我在學習紀錄裡留下這句話：

> 「先讀紀錄，再算統計，最後寫摘要」由 ADK 編排；「把統計寫成自然的兩句話」由 Gemini 生成。

這是在描述接下來要建立的目標架構。今天實際完成的，是離線流程練習與角色圖，還沒有把原本的 Bot 接上 ADK。

對我來說，先分清楚這件事很有幫助。原本已經寫好的統計，可以繼續由程式負責；Gemini 專心處理文案；接下來再用 ADK 組織它們如何合作。

至於這樣做之後，流程是否更容易理解、問題是否更好找，以及多出的依賴值不值得，仍然要等實作後拿前後版本比較。

今天先完成這一小步：跑過有資料與空資料的情境，畫出護照流程，也把資料庫、排程、模型與框架的角色分開。

之前每做一個功能，咖啡 Bot 就多學會一件事。這次，它成了我學新工具的教材。下一篇，就開始讓第一個 ADK agent 跑起來。
